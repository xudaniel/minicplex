# 补班 agent：一句话到方案的五步

**中文** | [English](README.en.md)

护士长随口说一句「下周三有人请假，常勤最多只能加 4 班」，程序给出三样东西：怎么补、多花多少、该谁签字。

这个目录和 minicplex 求解器本身没有依赖关系（求解用的是 Google OR-Tools）。放在这里，是因为它演示了优化模型在真实流程里的位置：**会说话的负责听，守规矩的负责拦，会算的负责算，最后由人签字。**

数字全部是一家虚拟诊所的自编数字，不代表任何真实机构。

## 跑起来

```bash
pip install ortools
cd learning/staffing-agent
python3 walkthrough.py            # 跟着主角那句话，一站一站打印
python3 walkthrough.py --all      # 主角 + 三个翻车现场 + 四道「考考你」
python3 walkthrough.py -i         # 自己一句一句输入，空行退出
python3 walkthrough.py "需求改成 1300 次"
python3 walkthrough.py --all --lang en   # 英文版：英文说法、英文输出
python3 -m unittest -v test_staffing_agent
```

## 五站流水线

| 站 | 函数 | 拿到什么 | 交出什么 |
|---|---|---|---|
| ① 助理 | `parse` | 一句话 | 改动单（每条附原话当收据） |
| ② 门卫 | `guard` | 改动单 + 原话 | ok／ask／reject／confirm |
| ③ 会计 | `apply` + `solve` | 放行的改动单 | 方案、费用、缺口 |
| ④ 老师傅 | `sanity` + `approver` | 方案 | 黄灯清单、谁来签 |
| ⑤ 秘书 | `explain` | 以上全部 | 一句人话 |

两条铁律：

1. **每站只做一件事，只认上一站交来的东西。**助理不算账，会计不听原话。
2. **任何一站说「不行」，后面全部停工。**宁可反问一句，也不交出一个错答案。

第 1 站现在用几条正则顶替大模型。换成真模型时只改 `parse()` 一个函数，后面四站一行不动：新助理不管多聪明，都要过同一道门。

## 主角那一趟

```
第 2 站｜门卫：✓ 原话 ✓ 一种班 ✓ 数字合理 ✓ 不用签字 → ok
第 3 站｜会计：派遣 8、常勤 4、加急 2
  次数 10×8 + 8×4 + 10×2 = 132 ≥ 130
  费用 50×8 + 32×4 + 75×2 = 678（平时 606）
第 4 站｜老师傅：没有黄灯；多花 72 > 50 → 院长批
第 5 站｜秘书：方案：派遣 8 班、常勤加排 4 班、加急派遣 2 班，费用 678（比基准多 72）。审批：院长批。
```

## 模型

```
决定：x[派遣]、x[常勤加排]、x[加急派遣] 为整数班数，short ≥ 0 为缺口
满足：10·x派遣 + 8·x常勤 + 10·x加急 + short ≥ 需求
      x加急 ≤ 20·y，x派遣 ≥ 8·y，y ∈ {0,1}     ← 合同：派遣用满才能叫加急
目标：最小化 50·x派遣 + 32·x常勤 + 75·x加急 + 1000·short
```

缺口罚 1000，是为了排不满时也能告诉你「还缺几次」，而不是只说无解；罚金要明显高于最贵的补法，后门才不会变成正门（罚 1 时求解器会一个班都不排）。

## 测试覆盖的情形

| 说法 | 结果 |
|---|---|
| 常勤最多只能加 4 班 | 678，院长批 |
| 需求到 140 次 | 656，护士长批 |
| 派遣涨价 10% | 641，护士长批 |
| 两三班吧（读不出） | 反问 |
| 需求 1300 次 | 拒绝 |
| 派遣最多 10 班 | 拒绝（超合同） |
| 加急被读成派遣 | 反问（收据里有两种班） |
| 加急 75 → 40 | 要确认；确认后 600 |
| 同上但拿掉合同规则 | 520，老师傅亮黄灯 |
| 常勤 4 班 + 需求 140 | 753，院长批 |
| 罚金改成 1 | 什么都不排，缺 130 |
