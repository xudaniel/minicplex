## 1. 一句话概述

用 C++17 从零实现一个“迷你版 CPLEX”：能读 CPLEX `.lp` 文件、能用 C++ 建模、能求解线性规划和混合整数规划，
代码短小、可读、每一步都能对照教科书理解。另有一份逐行移植的 Java 17 版，计算路径与 C++ 版完全相同。

## 2. 背景与动机

- CPLEX、Gurobi 等商业求解器是运筹优化的核心工具，但内部是黑盒，很难直观理解“单纯形法 + 分支定界”到底怎么跑。
- 作为决策自动化（ODM、业务规则）方向的产品经理，深入理解优化求解器的原理，有助于判断产品方向、
  与客户和工程团队对话（例如规则引擎与优化引擎如何配合）。
- 开源求解器（HiGHS、CBC、SCIP）代码量巨大，不适合作为入门阅读材料；市面上缺少“几千行以内、能真正跑题目”的教学型求解器。

## 3. 目标与非目标

### 3.1 目标

1. **能用**：正确求解中小规模 LP / MIP，结果可与暴力枚举或商业求解器对照。
2. **兼容**：读写 CPLEX LP 文件格式的常用子集，命令行体验接近 CPLEX。
3. **好读**：核心算法集中在少数几个文件里，注释清楚，适合学习与讲解。
4. **可验证**：自带测试，包括随机题目与暴力枚举的自动对比。

### 3.2 非目标

- 不追求与 CPLEX 比拼速度，不面向几万变量以上的大模型。
- 不实现二次规划（QP）、二阶锥（SOCP）、约束规划（CP）。
- 不做图形界面，不做商业化。

## 4. 目标用户与使用场景

| 用户 | 场景 |
|---|---|
| 学习运筹优化的学生 / 工程师 | 单步阅读单纯形和分支定界代码，理解算法 |
| 产品经理 / 售前 | 演示“优化求解器是什么、怎么建模”，用小例子讲清楚 |
| C++ 开发者 | 在没有商业许可证的环境下，给小项目嵌入一个轻量求解器 |
| 讲师 | 用 `examples/` 中的模型做课堂演示（生产计划、背包、选址） |

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 正确性 | 随机整数规划与暴力枚举 100% 一致；教科书例题结果正确 |
| 性能 | 几百个变量 / 约束的模型在 1 秒内求解（v1.0 稠密实现）；v2.0 起支持上千规模 |
| 可移植性 | 仅依赖 C++17 标准库与 CMake，Linux / macOS / Windows 均可编译 |
| 可读性 | 核心代码约 1,000 行，算法步骤有注释 |
| 数值稳定 | 统一的主元、最优性、整数性容差；防止退化循环 |

## 7. 成功指标

1. 测试全部通过，随机对比题数从 500 扩展到 5,000 仍保持 100% 一致。
2. 用 MIPLIB 中的小型题目（如 `p0033`、`flugpl`）求出公认最优值。
3. 一位没看过代码的工程师能在 1 小时内读懂单纯形与分支定界主流程。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 数值误差导致错判可行 / 不可行 | 结果错误 | 统一容差；随机对比测试；必要时引入缩放（scaling） |
| 稠密单纯形表规模受限 | 大模型很慢或内存不足 | v2.0 改为修正单纯形 + 稀疏 LU |
| LP 格式细节与 CPLEX 不完全一致 | 部分文件读不了 | 明确支持子集，读不了时给出行号和原因 |
| 整数变量无界时分支定界可能不终止 | 证明不了最优，达到节点上限 | 已记录为已知局限；v1.2 计划在搜索树内加割平面 |
| C++ 与 Java 两份代码分叉 | 两个版本结果不一致，维护翻倍 | 要求逐行对应；CI 每次提交逐题对比节点数和迭代次数，任何差异都会失败 |
| 业余时间有限 | 进度拖延 | 每个版本范围小、可独立发布 |

## 11. 附：v1.0 验收结果（2026-11-19）

- 单元测试 26 项、例子与命令行冒烟测试、基准模型可解性：全部通过（Release 与 ASan/UBSan 两种构建）
- 与 HiGHS 对拍：共约 6,000 道随机题（混合整数、较大混合题、纯 LP、多维背包）全部一致
- 对拍中发现 1 例 HiGHS 自身错误：LP 松弛无界的整数规划被报告为“最优 41”，实际可沿射线 (x1 + 7, x4 − 9)
  无限下降；minicplex 正确报告“不可行或无界”。对拍脚本已按 Meyer 定理处理此类情况
- 基准：单纯形迭代 777,609 → 40,804，总用时 2.78 秒 → 约 0.6 秒

## 12. 附：v1.1 整数规划提速验收（2026-11-19）

- 评测集（18 个整数规划）：节点 47,304 → 34,034（−28%），总用时快 1.7 倍；生产排程 7,001 → 419 个节点
- 正确性：单元测试 35 项（含 Gomory 割对 24,532 个整数点的有效性检验）、ASan/UBSan 通过；与 HiGHS 对拍约 4,000 道全部一致
- 对拍抓到并修复 1 个真实 bug：单纯形表漂移导致接受违反约束 3×10⁻⁵ 的伪解，已用“按原始矩阵复核 + 解抛光”修复
- 取舍：小模型（如员工排班）上强分支和割平面的开销会超过收益（0.016 秒 → 0.06 秒），大模型上收益明显

## 13. 附：Java 版验收（2026-11-19）

- 范围：求解器、命令行（含 `--trace`）、基准与随机题工具、15 个例子、测试全部移植；Java 17 起可用，零依赖；`build.sh`（不联网）和 Maven 两种构建
- 一致性：15 个例子输出和导出的 `.lp` 逐字相同；`--trace` 逐行相同；13 个基准模型、2,000 道随机混合整数题的状态、目标值、节点数、迭代次数全部相同
- 正确性：Java 版自己的 40 项测试全部通过（暴力枚举 500 题 × 3 套参数、Gomory 割有效性、影子价格扰动核对等）
- 移植中发现并修复 C++ 版 1 个确定性问题：割平面和强分支候选用不稳定排序、节点队列平局无规则，搜索路径依赖标准库实现。改为稳定排序 + 插入顺序平局规则
- 速度：基准模型总用时 Java 约 0.72 秒，C++ 约 0.39 秒
